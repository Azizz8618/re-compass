# Передача адреса переменной через BDVECT

Проверено на эмуляторе 23.11.2026. Все прогоны - на рабочих копиях дисков в `/tmp/.private/azizz/opencode/bdvect-work/`, оригинальные образы не изменялись.

## Результаты экспериментов

| Номер | Проверка | Результат |
|---|---|---|
| F1 | внешняя процедура `SETVAL(VAR P:INTEGER; V:INTEGER)`, `P:=V` | `SETVAL X= 777` |
| F2 | `BDVECT[k].P := REF(P)` во внешней процедуре, затем `Q := BDVECT[11].P; Q^ := 999` | `DEREF X= 999`, адрес фактической переменной |
| F3 | адрес как `integer`: `N := BDVECT[11].I`, `W.I := N`, `BDVECT[11] := W` | `ROUNDTRIP X= 555`; также `ORD(REF(X))` и `PTR(...)` работают |
| F4 | сквозной тест: `TPCMPAD1(VAR P:INTEGER; K:INTEGER)` кладёт `REF(P)` в `BDVECT[K]`, затем `COPD=22c`, `BDVECT[13].I:=4c`, `PASBD` | `X= 111111`, контроль через `GETD` тоже `111111` |
| F5 | общий `BDVECT` виден внешнему модулю и главной программе при `PROGRAM ...(OUTPUT,BDVECT)` в обоих | подтверждено |
| F6 | `VAR P;` без типа | ошибка 106 `ТРЕБУЕТСЯ ДВОЕТОЧИЕ`, то же для `FORTRAN`; `VAR P:ALFA` не принимает `integer` (ошибка 40) |

Важная деталь F4: при `BDVECT[13].I := 1c` МАРС выдал `14 ДЛ.ЗАП>ДЛИН`. Длина должна равняться длине записи (4 слова).

Precedent в исходниках: `experiment.b6:74` использует `bdvect[11].p := ref(a)`, `sorucom.b6:64` читает длину из `bdvect[39]`.

## Вывод

Сигнатуру `TPCMPAD1(VAR P)` буквально перенести нельзя. рабочий вариант -семейство типизированных внешних процедур:

```pascal
PROCEDURE TPCMPAD1I(VAR P:INTEGER; K:INTEGER); EXTERNAL;
PROCEDURE TPCMPAD1A(VAR P:ALFA;    K:INTEGER); EXTERNAL;
PROCEDURE TPCMPAD1B(VAR P:BOOLEAN; K:INTEGER); EXTERNAL;
PROCEDURE TPCMPAD1P(VAR P:POINTER; K:INTEGER); EXTERNAL;
```

Каждая пишет `BDVECT[K].P := REF(P)`, что эквивалентно `BDVECT[K].I := ORD(REF(P))`. Для нескольких аргументов в одном блоке использовать возрастающие слоты. `BDVECT` объявляется в главной программе как `PROGRAM name(OUTPUT,BDVECT)`.

## Инвентаризация вызовов

- `UCOMPAS.PAS`: 27 вхождений, из них 24 живых при `{$DEFINE FORCE}`. Аргументы: `Number`/`KnotNumber`/`R`/`Key` (`longint`), `SchemeSpace` (указатель), один неявно типизированный `Key` в строке 281.
- `TSSPPR.PAS`: 40 вхождений, 30 живых. В основном `integer`, четыре `alf6`, четыре `boolean`, один `pointer`.
- Другие модули (`CMPSNO`, `GSC`, `UNPIC`, `ISCHEME`, `GT1`): ещё 22 вхождения.

Итого около 15 не-integer вызовов требуют переименования на типизированную обёртку; остальные (~70) остаются как есть.

## Сравнение вариантов

| Критерий | BDVECT + REF | Переписывание вызывающих на значения |
|---|---|---|
| Доказанность | F1-F5, включая запись МАРСом в переменную | гипотеза |
| Правки верхних слоёв | около 15 вызовов | около 80 блоков `TPCMPP1`/`TPCMPIN1` |
| Выходные параметры | работают как в PC | нужен явный copy-back |
| Риск | коллизии слотов `[8]`, `[11]`, `[13]`, `[31]`, `[39]` | несовместимость типов |

## Рекомендация

Выбрать BDVECT + `REF`. Это единственный вариант, воспроизводящий контракт PC «микрокод получает адрес переменной» и проверенный сквозным прогоном.

Остаётся непроверенным: совместимость с реально эмулируемой `PIC.L` (в PC адрес занимал два слова), выбор слотов для нескольких адресов и отсутствие коллизий с `[31]`/`[39]`. Следующий шаг - прогнать через обёртку реальный блок `CGetBdKey` (`UCOMPAS.PAS:103-115`).

Артефакты: `/tmp/.private/azizz/opencode/bdvect-work/exp{1..9}.b6` и соответствующие `.run`/`.err`.

## Проверка четырех оберток в одном блоке

В модуле `twaddr.pas` (scratch `/tmp/.private/azizz/opencode/typed-wrappers/`) объявлены `(*=e+*)procedure TCMPAD1I/A/B/P(var p: integer/alfa/boolean/@integer; k: integer)`, каждая пишет `BDVECT[k].P := REF(P)`. Модуль собран в PERSO рабочей копии 2348 (`ДЛИНА LIBRARY 031 ЗОН`, без ошибок).

Тест вызвал все четыре обёртки в одном блоке со слотами `[10]`, `[12]`, `[14]`, `[16]`:

```text
SLOT10= 0000000000001432 SLOT12= 0000000000001440
SLOT14= 0000000000001442 SLOT16= 0000000000001443
ADDR NONZERO AND DISTINCT=    TRUE
MARS FIND KEY=III.
SLOTS STABLE AFTER MARS=    TRUE
RESERVED 11 13 39 STABLE=    TRUE
X=       777 A=XYZ    F=   FALSE PP^=       777
```

Факты: адреса различны и ненулевые; МАРС `FIND` прочитал ключ из `[8]` и выдал `III.` в `[31]`; слоты `[11]/[13]/[39]` не тронуты; запись через адреса изменила `integer`, `alfa`, `boolean` и указатель.

Ограничение имён: Паскаль-Монитор 15.1 обрезает идентификатор до 8 символов. `TPCMPAD1I` (9) и `TPCMPAD1A` сводятся к одному имени и дают `******2 ИДЕНТИФИКАТОР УЖЕ ОПРЕДЕЛЕН`. Режим `s7` это не обходит. Имена формальных параметров тоже обязаны быть разными во всех процедурах. В рабочем модуле `src/comtup.pas` используются 7-символьные имена `TPCMP1I/A/B/P`, то есть ограничение соблюдено.

ФАКТ: оба способа кодирования адреса проверены на эмуляторе (`verify_ord.b6`). `ORD(REF(P))` даёт тегированное слово: две старшие восьмеричные цифры `64`, дальше адрес; `.P := REF(P)` даёт тот же адрес без тега. `PTR` снимает тег `64`.

```text
ORD i= 6400000000001550  P i= 0000000000001551
ORD a= 6400000000001552  P a= 0000000000001553
ORD b= 6400000000001554  P b= 0000000000001555
ORD p= 6400000000001556  P p= 0000000000001557
```

Микрокоманда `COPD = 22c` с длиной `BDVECT[13].I = 4c` корректно записала `111111` по адресу в обоих представлениях для всех четырёх типов, включая `alfa` и `boolean`. Ошибок нет. Поэтому патч `src/comtup.pas` не требуется: строки 142, 149, 156, 163 могут оставаться как `BDVECT[k].I := ORD(REF(P))`. Альтернатива `.P := REF(P)` тоже рабочая, если нужен чистый адрес.

ГИПОТЕЗА, не проверялась: `SaveAdr` копирует тегированное слово `BDVECT[k].I` в `PIC.L[na]`. Если потребитель `PIC.L` ожидает чистый адрес, тег `64` может помешать. Это отдельный вопрос, к записи через `BDVECT` и МАРС отношения не имеет; проверять его нужно с реальным интерпретатором `PIC`.
